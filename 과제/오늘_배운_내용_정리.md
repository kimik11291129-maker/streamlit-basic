## 1. Streamlit 기초 — 위젯 & 레이아웃

### 1.1 `st.navigation` / `st.Page`로 멀티페이지 구성
사이드바에 `pages/` 폴더를 자동 인식시키는 방식 대신, 함수를 명시적으로 등록하는 방식을 사용했다.

```python
pages = {
    "카테고리명": [
        st.Page(render_func, title="제목", icon="🎛️", default=True),
        st.Page(other_func, title="제목2", icon="📐"),
    ],
}
st.navigation(pages).run()
```

- 각 페이지는 **함수**로 정의하고, 함수 안에서 `st.title()` 등을 호출한다.
- `st.set_page_config()`는 앱 전체에서 **딱 한 번**, 가장 먼저 호출해야 한다.
- 페이지 함수 안에서 `with st.sidebar:` 를 또 써도 내비게이션 목록 아래에 자연스럽게 이어붙는다.

### 1.2 탭으로 계층 구조 만들기
카테고리(페이지) → 하위 기능(탭)의 2단 구조를 `st.tabs()`로 구현했다.

```python
tab1, tab2 = st.tabs(["🔘 선택 & 버튼", "✍️ 텍스트 & 숫자"])
with tab1:
    render_buttons_and_selection()
```

## 2. OpenAI API 연동

### 2.1 기본 호출 구조
```python
from openai import OpenAI
client = OpenAI(api_key=api_key)
response = client.chat.completions.create(model=model, messages=messages)
answer = response.choices[0].message.content
```

- `messages`는 `{"role": "user"/"assistant", "content": ...}` 리스트.
- 이미지 첨부 시 `content`를 리스트로 만들고 `{"type": "image_url", "image_url": {"url": f"data:{mime};base64,{encoded}"}}` 형태를 섞어 넣는다(Vision 입력).

### 2.2 최신 모델 정보는 **추측하지 말고 문서로 확인**
모델 지식(학습 시점)이 실제 서비스보다 오래될 수 있다는 걸 이번에 직접 겪었다. `gpt-4o-mini`로 알고 있었지만, 실제로는 `gpt-5.5`, `gpt-5.6-*`, `gpt-6-astra` 등 더 최신 모델이 나와 있었다. **`WebSearch`/`WebFetch`로 공식 문서(`developers.openai.com/api/docs/models`)를 직접 조회**해서 실제 모델 ID를 확인했다.

### 2.3 API 키 우선순위 체인 설계
배포 환경과 로컬 환경, 사용자 지정 키를 모두 지원하려면 폴백 체인이 필요하다.

```python
def resolve_api_key():
    if st.session_state.get("user_api_key"):      # 1순위: 사용자가 직접 등록
        return st.session_state.user_api_key, "수동 등록"
    try:
        if "OPENAI_API_KEY" in st.secrets:          # 2순위: 배포(st.secrets)
            return st.secrets["OPENAI_API_KEY"], "st.secrets (배포)"
    except Exception:
        pass
    env_key = os.getenv("OPENAI_API_KEY")           # 3순위: 로컬(.env)
    if env_key:
        return env_key, ".env (로컬)"
    return None, None
```

**배운 포인트**: `st.secrets`는 `secrets.toml` 파일이 없으면 **접근하는 순간 예외**를 던진다. 이런 경우엔 방어 코드를 지양하는 원칙의 예외로 두고 `try/except` 한 곳만 허용했다.

## 3. SQLite 연동 & 데이터 보관 정책

### 3.1 스키마 설계
```sql
CREATE TABLE conversations (id, name, created_at, updated_at);
CREATE TABLE messages (id, conversation_id, role, content, created_at,
                        FOREIGN KEY(conversation_id) REFERENCES conversations(id));
```

- SQLite는 **FK CASCADE가 기본이 아니다** → 부모(conversations) 삭제 전에 자식(messages)을 먼저 지워야 고아 행이 안 남는다.

### 3.2 정렬 버그: `created_at` vs `id`
`CURRENT_TIMESTAMP`는 **초 단위**라서, 같은 초에 저장된 user/assistant 메시지가 `ORDER BY created_at`으로는 순서가 뒤집힐 수 있다. → **`ORDER BY id`**로 바꿔서 삽입 순서를 보장하는 게 더 안전하다는 걸 배웠다.

### 3.3 "N개까지만 보관, 초과 시 오래된 것부터 삭제" 패턴
```python
# 세션당 최대 턴 수 제한
c.execute("""
DELETE FROM messages WHERE id IN (
    SELECT id FROM messages WHERE conversation_id = ? ORDER BY id ASC LIMIT ?
)
""", (conversation_id, excess))

# 전체 세션 수 제한 (오래 안 쓴 것부터)
c.execute("SELECT id FROM conversations ORDER BY updated_at DESC LIMIT -1 OFFSET ?", (MAX_SESSIONS,))
```

- **1턴 = user 1행 + assistant 1행**을 항상 같이 저장/삭제해야 짝이 안 깨진다.
- DB만 자르면 화면에 든 `st.session_state.messages`와 어긋나므로 **메모리도 같이 잘라줘야** 한다.
- API에 보낼 대화 맥락도 전체(100턴)가 아니라 **최근 일부(20턴)만** 보내야 요청마다 토큰 비용이 안 튄다.

### 3.4 검증 방법 — 임시 스크립트로 직접 확인
"아마 될 것"이라고 넘어가지 않고, scratchpad에 검증 스크립트를 짜서 실제로 105턴/12세션을 넣어보고 결과(100턴 유지, 10세션 유지, 고아 행 0건)를 눈으로 확인했다. **말로 설명하는 것과 실제로 돌려서 숫자를 보는 것은 다르다.**

## 4. 보안

### 4.1 "키가 노출된 것 같다"는 상황에서 확인하는 절차
1. `git log --all -p -- .env` 로 그 파일이 **애초에 커밋된 적 있는지** 확인
2. `git log --all -p | grep -E "sk-[A-Za-z0-9]{10,}"` 로 히스토리 전체에서 **실제 키 패턴**을 찾기
3. placeholder(`sk-your-api-key-here`)와 진짜 키를 구분 — GitHub Secret Scanning은 `sk-` 접두어만 보고도 플래그를 걸 수 있어서 **오탐(false positive)**이 흔하다
4. `git check-ignore -v .env` 로 `.gitignore`가 실제로 그 파일을 잡고 있는지 확인

### 4.2 배운 것: "저장 안 하는 코드"만으로는 부족하다
API 키를 DB에 저장하는 코드는 없었지만, **사용자가 채팅창에 키를 직접 붙여넣으면** 그 텍스트가 "메시지 내용"으로 DB에 그대로 저장되는 경로가 있었다. 코드 경로(어떤 함수가 뭘 쓰는지)만 감사하는 걸로는 부족하고, **"사용자가 실수로 입력하면 어떻게 되는가"**까지 생각해야 한다는 걸 배웠다. 대응: 입력 시점에 `sk-[A-Za-z0-9_-]{16,}` 정규식으로 자동 치환.

### 4.3 실제로 DB 파일 바이트까지 뒤져서 검증
"코드상 문제없어 보인다"에서 멈추지 않고, 실제 `.db` 파일을 바이트 단위로 읽어서 키 문자열이 물리적으로 존재하는지(`FAKE_KEY.encode() in raw`) 확인했다.

### 4.4 로그인 게이트 설계 원칙
`.env`나 `st.secrets`에 키가 이미 있어도 **로그인 화면을 반드시 한 번 거치게** 만들었다 — 보안 안내 메시지를 모든 사용자가 보게 하기 위한 의도적 설계.

## 5. Git / GitHub

### 5.1 새 저장소에 처음 연결하기
```bash
git remote add origin <URL>
git branch -M main
git push -u origin main
```

### 5.2 커밋 전 체크리스트
- `git status` → 뭐가 올라가는지 확인 (특히 `git add -A` 이후 재확인)
- `.claude/settings.local.json` 같은 **개인 로컬 설정은 gitignore** (팀/공유용 `settings.json`과 구분)
- `.env`, DB 파일(`chat_history.db`) 등 **런타임에 생기는 로컬 파일**도 gitignore
- 커밋 메시지는 **"무엇을 바꿨는지"보다 "왜 바꿨는지"** 위주로

### 5.3 권한 프롬프트 줄이기
반복적으로 뜨는 승인 창(예: `git commit`)을 `~/.claude/settings.json`의 `permissions.allow`에 패턴(`"Bash(git *)"`)으로 등록해두면 매번 묻지 않는다.

## 6. 코드 구조화 — 리팩토링

### 6.1 단일 파일이 커지면 역할별로 쪼갠다
`app2.py` 499줄 → 7개 모듈로 분리:

```
app2.py            진입점(게이트 + 내비게이션)
chat/config.py     상수 + 키 해석
chat/database.py   스키마 + CRUD + 보관 정책
chat/login_page.py 로그인 + 보안 안내
chat/chat_page.py  채팅

chat/styles.py     공통 CSS
```

**기준**: "이 함수/블록이 담당하는 책임이 뭔가"로 나눈다 — 설정, 저장소, 화면(페이지) 단위로 쪼개면 각 파일이 200줄 안팎으로 줄어들고 어디를 고쳐야 할지 명확해진다.

### 6.2 두 개의 독립 앱을 하나의 내비게이션으로 묶기
`app2.py`(채팅)와 `app2_history.py`(히스토리)가 원래 **별도 프로세스**로 실행해야 했는데, `main()`을 `render_xxx_page()` 형태의 **호출 가능한 함수**로 바꾸고 `st.Page(func)`로 등록하면 **한 프로세스 안에서 사이드바 클릭으로 이동**하게 만들 수 있다. 단, `st.set_page_config()`는 진입점에서 한 번만 호출해야 하므로 각 모듈에서는 제거하고 진입점에만 남긴다.

## 7. 테스트

### 7.1 Streamlit 공식 테스트 프레임워크 — `AppTest`
`curl`로 앱에 요청해서 HTTP 200이 오는 건 **SPA 껍데기가 응답한다는 것**만 확인할 뿐, 실제 파이썬 스크립트가 에러 없이 실행됐는지는 보장하지 않는다. 실제 스크립트 실행/렌더 결과를 확인하려면:

```python
from streamlit.testing.v1 import AppTest

at = AppTest.from_file("app2.py", default_timeout=30)
at.session_state["authenticated"] = True
at.run()

at.exception          # 실행 중 발생한 예외 목록
at.title              # 렌더된 제목들
at.chat_input         # 채팅 입력창 요소들
at.sidebar.button     # 사이드바 버튼들
```

### 7.2 임시 검증 스크립트는 scratchpad에
DB 정책 검증, 키 유출 검증처럼 **1회성으로 확인만 하면 되는 스크립트**는 프로젝트에 남기지 않고 세션 scratchpad 디렉터리에 작성 후 실행하고 버린다. 프로젝트에는 결과(수정된 코드)만 남긴다.

## 8. 기타

### 8.1 SVG → PNG 변환 (별도 도구 설치 없이)
Node/Python에 SVG 렌더링 라이브러리가 없어도, **Windows에 이미 깔려 있는 Edge 브라우저의 headless 스크린샷 기능**으로 변환했다.

```powershell
& "C:\Program Files (x86)\Microsoft\Edge\Application\msedge.exe" `
  --headless=new --disable-gpu `
  --screenshot="출력경로.png" --window-size=800,600 `
  "file:///절대경로/파일.svg"
```

`--headless`(구버전)가 안 되면 `--headless=new`를 시도한다. Bash에서 GUI 실행파일을 호출하면 stdout이 안 잡히는 경우가 있어, `PowerShell`의 `Start-Process -Wait -RedirectStandardError`로 종료 코드와 로그를 확실히 확보했다.

## 9. 오늘의 핵심 교훈 (요약)

1. **모델/API 지식은 오래될 수 있다** — 확신 없으면 공식 문서를 직접 조회한다.
2. **"코드에 없다"와 "실제로 안 일어난다"는 다르다** — 사용자 입력 경로까지 포함해서 취약점을 생각한다.
3. **검증은 실행해서 숫자로 확인한다** — 스크립트를 짜서 105턴/12세션 같은 경계 케이스를 직접 넣어본다.
4. **HTTP 200 ≠ 앱 정상 동작** — 실제 프레임워크 테스트 도구(`AppTest`)로 스크립트 실행 자체를 검증한다.
5. **보안 오탐과 실제 유출을 구분한다** — `.gitignore` 여부, git 히스토리, 실제 파일 바이트까지 확인하고 나서 결론 낸다.
6. **역할별로 파일을 쪼개면 유지보수가 쉬워진다** — 한 파일이 500줄을 넘으면 책임 단위로 분리 신호다.
