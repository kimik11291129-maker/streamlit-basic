# AI 채팅 앱 구현계획서

**대상 앱**: `app2.py` (OpenAI API 기반 AI 채팅)
**작성일**: 2026-09-17

## 1. 배경 및 문제 정의

기존 `app2.py`는 채팅, 이미지/파일 첨부, SQLite 저장, 히스토리 조회가 **단일 파일 499줄**에 모두 들어 있었다. 여기에 다음 문제가 있었다.

| # | 문제 | 영향 |
|---|---|---|
| 1 | `.env`가 존재하면 수동 키 입력창이 **숨겨짐** | 키를 변경하거나 다른 키로 사용할 방법이 없음 |
| 2 | `.env`는 gitignore 대상 → **배포본에 미포함** | 배포된 Streamlit 페이지는 키가 없어 동작 불가 |
| 3 | 인증 게이트 없음 | 공개 URL이므로 누구나 즉시 채팅 사용 가능 |
| 4 | 대화 저장 **무제한** | DB 증가 + 요청마다 전체 맥락 전송으로 토큰 비용 급증 |
| 5 | 첨부 기능이 범위를 넓힘 | 과제 요구("채팅 + 내역 열람")와 불일치 |

## 4. 상세 설계

### 4.1 API 키 처리 (FR-1)

`chat/config.py`의 `resolve_api_key()`가 아래 순서로 키를 찾는다.

| 순위 | 소스 | 용도 |
|---|---|---|
| 1 | `st.session_state["user_api_key"]` | 사용자가 로그인 화면에서 등록한 키 |
| 2 | `st.secrets["OPENAI_API_KEY"]` | 배포 환경 (Streamlit Cloud Secrets) |
| 3 | `os.getenv("OPENAI_API_KEY")` | 로컬 개발 (`.env`) |

**수동 등록 키를 1순위**에 둔 것이 핵심이다. 서버에 키가 있어도 사용자가 자신의 키로 덮어쓸 수 있어야 FR-1의 "키 등록 옵션"이 실제로 동작한다.

`secrets.toml`이 없는 환경에서는 `st.secrets` 접근만으로 예외가 발생하므로 이 지점 한 곳에만 `try`를 둔다. 프로젝트 규칙(방어 코드 지양)의 의도적 예외이며, 없으면 로컬 실행 시 앱이 즉시 죽는다.

반환값에 **출처 문자열**을 함께 돌려 UI에 배지로 표시한다(`수동 등록` / `st.secrets (배포)` / `.env (로컬)`).

### 4.2 로그인 및 보안 안내 (FR-3)

`app2.py`가 `st.session_state["authenticated"]`를 확인하고, 미인증이면 로그인 페이지를 렌더한 뒤 `st.stop()`으로 중단한다. 내비게이션 자체를 만들지 않으므로 채팅/내역 페이지에 접근할 수 없다.

로그인 화면에 노출하는 **보안 취약점 안내**:

- **인증 체계 없음** — 학습·데모용이며 공개 URL이므로 주소를 아는 누구나 접근 가능
- **API 키 보관 방식** — 서버 세션 메모리에만 보관, DB·파일에 저장하지 않음, 서버 재시작 시 소멸
- **채팅 내용 평문 저장** — SQLite에 암호화 없이 저장되므로 개인정보·비밀번호 입력 금지
- **채팅창에 키 입력 금지** — 채팅 내용은 DB에 남음 (자동 차단 장치는 4.4 참조)
- **과금 주의** — 사용량 한도를 건 테스트 전용 키 권장
- **공용 PC** — 사용 후 반드시 로그아웃
- **유출 대응** — platform.openai.com에서 즉시 폐기(revoke)

로그아웃은 `st.session_state.clear()`로 세션을 비워 로그인 화면으로 되돌린다.

### 4.3 저장 보관 정책 (FR-4, FR-5)

```python
MAX_TURNS_PER_SESSION = 100   # 1턴 = user 1행 + assistant 1행
MAX_SESSIONS = 10
API_HISTORY_TURNS = 20        # API 전송 맥락 제한
```

**턴 단위 저장** — `save_turn()`이 user/assistant 두 행을 항상 함께 삽입한다. 개별 저장 시 트리밍 과정에서 질문만 남고 답변이 잘리는 짝 깨짐이 발생할 수 있기 때문이다.

**`trim_messages()`** — 저장 직후 호출. 해당 대화의 행 수가 200(100턴 × 2)을 넘으면 `id` 오름차순으로 초과분을 삭제한다.

**`trim_sessions()`** — 새 대화 생성 직후 호출. `updated_at DESC` 기준 상위 10개만 남기고 나머지를 삭제한다. "오래된 세션"은 *마지막 사용이 가장 오래된 세션*으로 해석했다. FK CASCADE가 없으므로 **자식 `messages`를 먼저 삭제**해 고아 행을 방지한다.

**빈 세션 문제 회피** — "새 대화" 버튼은 DB 행을 만들지 않고 세션 상태만 초기화한다. DB 행은 첫 메시지를 보낼 때 생성된다. 그렇지 않으면 버튼만 눌러도 10개 한도가 빈 세션으로 차 버린다.

**세션 메모리 동기화** — DB만 자르면 화면(`st.session_state.messages`)과 어긋나므로, 전송 후 메모리도 동일한 200행 한도로 절단한다.

**API 맥락 제한** — 요구사항에는 없으나, 100턴이 쌓이면 매 요청마다 200개 메시지를 전송해 토큰 비용이 급증한다. 최근 20턴만 전송하도록 제한했다.

### 4.4 보안 설계

**키가 DB에 저장되지 않음을 구조적으로 보장**

DB에 쓰는 SQL은 3개뿐이며, 어느 것도 키를 다루지 않는다.

| 구문 | 저장 값 |
|---|---|
| `INSERT INTO conversations` | 대화 이름 |
| `INSERT INTO messages` | conversation_id, role, content |
| `UPDATE conversations` | updated_at |

API 키는 `st.session_state` → `OpenAI(api_key=...)` 경로로만 흐르며 `database.py`에 도달하지 않는다.

**잔여 위험과 대응**

검증 과정에서 **사용자가 채팅창에 키를 직접 붙여넣으면 메시지 본문으로 DB에 평문 저장되는 경로**를 발견했다. 이를 막기 위해 입력 시점에 `sk-[A-Za-z0-9_-]{16,}` 패턴을 `[API 키 삭제됨]`으로 치환한다. 화면·DB·API 전송 어디에도 원문이 남지 않으며, 치환 시 사용자에게 토스트로 알린다.

**화면 표시** — 키는 항상 `sk-proj••••••••fXYZ` 형태로 마스킹한다.

**gitignore 대상** — `.env`, `chat_history.db`, `.streamlit/secrets.toml`, `.claude/settings.local.json`

### 4.5 디자인 리뉴얼 (FR-6)

- **채팅**: 첨부 패널을 제거해 전체 폭 사용, 말풍선 스타일(사용자/AI 배경색 구분), 최대 폭 900px
- **빈 상태**: 안내 카드 + 예시 프롬프트 버튼 3개
- **헤더**: 현재 대화명 + 턴 사용량 프로그레스 바(`37 / 100턴`)
- **사이드바 3단**: 계정(출처 배지·마스킹 키·로그아웃) → 대화 목록(`3/10`) → 설정(모델)
- **내역 페이지**: 검색 + 목록, 상단에 보관 정책 안내
- CSS는 `styles.py`에서 1회 주입, 테마 색상은 `.streamlit/config.toml`로 통일

## 5. 데이터베이스 설계

```sql
CREATE TABLE conversations (
    id          INTEGER PRIMARY KEY AUTOINCREMENT,
    name        TEXT NOT NULL,
    created_at  TIMESTAMP DEFAULT CURRENT_TIMESTAMP,
    updated_at  TIMESTAMP DEFAULT CURRENT_TIMESTAMP
);

CREATE TABLE messages (
    id               INTEGER PRIMARY KEY AUTOINCREMENT,
    conversation_id  INTEGER NOT NULL,
    role             TEXT NOT NULL,      -- 'user' | 'assistant'
    content          TEXT NOT NULL,
    created_at       TIMESTAMP DEFAULT CURRENT_TIMESTAMP,
    FOREIGN KEY(conversation_id) REFERENCES conversations(id)
);
```

첨부 기능 제거에 따라 기존 `image_filename`, `file_filename` 컬럼을 삭제했다. 스키마가 바뀌므로 기존 DB는 `chat_history.db.bak`으로 **백업 후 재생성**했다(삭제하지 않아 되돌릴 수 있음).

**정렬 기준 변경 (버그 수정)** — 기존에는 `ORDER BY created_at`으로 조회했다. `CURRENT_TIMESTAMP`는 **초 단위**라 질문과 답변이 같은 초에 저장되면 순서가 뒤집힐 수 있었다. `ORDER BY id`로 변경해 삽입 순서를 보장한다. 트리밍도 동일하게 `id` 기준으로 동작한다.

## 7. 한계 및 후속 과제

- **실제 API 호출 미검증** — 과금이 발생하므로 자동 검증에서 제외했다. 모델 ID(`gpt-5.6-terra` 등)가 해당 계정에서 호출 가능한지는 브라우저에서 1회 전송해 확인해야 한다. 실패 시 접근 가능한 모델로 목록 조정이 필요하다.
- **인증 강도** — API 키 보유 여부만 확인하므로 사용자 식별·권한 구분이 없다. 다중 사용자 환경에는 별도 인증 체계가 필요하다.
- **DB 격리 없음** — 모든 사용자가 같은 SQLite 파일을 공유한다. 배포 환경에서 여러 명이 접속하면 대화 내역이 서로 보인다. 사용자별 분리가 필요하면 세션 식별자를 스키마에 추가해야 한다.
- **채팅 내용 암호화 없음** — 평문 저장이므로 민감 정보 입력을 금지하는 안내로만 대응하고 있다.
